# Задача 2. Эксперимент: цепочки против открытой адресации

Справочник (`cache.py`) хранит кэш и каталог в своей хэш-таблице (`hashtable.py`), встроенные
`dict`/`set` не используются. Сравнивались две реализации таблицы с одинаковым интерфейсом
(`get`, `insert`, `remove`):

| Ветка | Стратегия | Как устроена |
|---|---|---|
| `ke2517kda74/experiment/chaining` | метод цепочек | массив корзин, в корзине - список пар; при заполнении > 1 массив удваивается |
| `ke2517kda74/experiment/open-addressing` | открытая адресация | пары прямо в массиве ячеек, линейное пробирование, «надгробия» при удалении; при заполнении > 1/2 массив перестраивается |

Обе ветки начаты от `ke2517kda74/develop` и проходят все открытые тесты (`python tools/check.py 2` - 70/70).

## Как мерили
Скрипт генерирует каталог из N записей (`SKU-i; товар номер i`) и 3·N команд: 80 % `get`
существующего артикула, 5 % `get` несуществующего, 10 % `put`, 5 % `del`, в конце `list`.
Программа запускается целиком (`python cache.py catalog.txt --size L < commands.txt`), берётся медиана
из 3 запусков. Время включает запуск интерпретатора (~0.04 с), чтение каталога и все команды.
Вывод обеих версий сравнивался побайтно - он совпадает во всех замерах.

Компьютер: AMD64 (Family 23), Windows 10, Python 3.14.8.

## Вывод
- На 10 и 1 000 записей разницы нет: время почти целиком уходит на запуск Python.
- На 100 000 записей открытая адресация быстрее на 7-8 % (2.70-2.97 с против 2.89-3.20 с).
  Пары лежат в двух плоских списках, и не нужно создавать отдельный список на каждую корзину
  и пару `[ключ, значение]`. Перестройка массива тоже дешевле.
- Минус открытой адресации - «надгробия» после частых `del`. Но они убираются при перестройке,
  а в справочнике удалений немного.
